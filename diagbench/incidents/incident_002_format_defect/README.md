# Incident 002 — Missing Provisioning Effect from Reference-Shape Defect

Incident Family 002 is a deterministic synthetic benchmark family in which an
operation executor performs an exact external-reference lookup without the
required input validation or normalization. Healthy references share one
generated ASCII structural signature. The target has exactly one compatible
shape defect, its lookup misses, and no provisioning effect is created.

The checked-in `incident.json` is development seed `1001`, generated by
`incident-002-generator-v1`. Generation is intentionally restricted to the
development seed range `1000–1999` while the family is being constructed.

## Model-visible evidence

The exclusive `ModelView` contains a neutral troubleshooting question plus:

- `processing_attempts`: receipt/completion time, operation identity, sensitive
  external reference, intake/executor aliases, final state, and effect flag;
- `lookup_observations`: exact-lookup results, time, latency, operation and
  sensitive external-reference identity, and dependency alias;
- `effect_records`: created destination effects for healthy controls;
- `dependency_health`: bounded health samples and warnings without outage; and
- neutral logs that report lifecycle events without naming the cause.

The evidence includes at least five healthy controls around the target, one
successful high-latency control, and one healthy control whose initial lookup
misses before a successful recovery. Consequently, neither latency nor a lookup
miss alone uniquely identifies the intended cause.

## Hidden oracle

The v2 oracle is:

```text
observed_outcome = missing_effect
trigger = malformed_or_unexpected_input
subsequent_action = no_follow_on_action
failure_mechanism = validation_or_input_handling_failure
affected_component = operation_executor
```

The generated structural template, defect class and position, latent valid
target reference, sensitive-field annotations, invariants, evidence rubric,
component mappings, and oracle labels remain outside `ModelView`.

## Structural evidence

Incident 002 uses `structural-signature-v1`. Printable ASCII uppercase letters
map to `U`, lowercase letters to `l`, digits to `D`, and literal punctuation or
spaces remain unchanged. Thus `AB-1234-xY` becomes `UU-DDDD-lU`.

The family supports only missing/extra separators, final truncation, internal
fixed-width insertion or deletion, leading numeric-run width loss generated by
removing a leading zero, and one uppercase/lowercase class mismatch. The
defect-signature invariant recomputes the target/control signatures from visible
values; it does not accept hidden defect metadata as proof.

For the constrained leading-zero case, `defect_class = leading_zero_loss`
remains hidden construction metadata. The observable invariant instead records
`numeric_run_leading_position_deletion`: healthy controls require a fixed-width
digit run and the target signature is the expected signature with the run's
leading `D` position removed. It makes no claim about the literal value of that
unobserved digit. Passing the hidden label `leading_zero_loss` to the generic
visible-signature predicate is rejected.

## Research scope

This family is designed to test whether retaining visible shape contributes RCA
utility beyond retaining equality and linkage. It is synthetic and has not yet
been validated with humans or providers. No Incident 002 validation or held-out
instance has been generated or inspected during construction.
