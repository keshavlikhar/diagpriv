# Incident 003 — Inconsistent State from Premature Compensation

Incident Family 003 is a deterministic synthetic benchmark family in which a
workflow orchestrator reaches its deadline while downstream execution remains
legitimately in progress. The orchestrator begins compensation, the original
execution later succeeds, and the final compensated workflow state coexists
with an active original effect.

The checked-in `incident.json` is development seed `1001`, generated by
`incident-003-generator-v1` under `incident-003-temporal-protocol-v1` and
`temporal-semantics-v1`. Construction rejects every seed outside development
range `1000–1999`.

## Model-visible evidence

The exclusive `ModelView` contains a neutral troubleshooting question plus:

- `workflow_attempts`: dispatch, deadline, compensation state, final workflow
  state, operation identity, and orchestrator alias;
- `execution_observations`: start/completion times, result, operation identity,
  and executor alias;
- `effect_records`: effects that actually exist, including creation time and
  state;
- `compensation_records`: actual compensation intervals and results;
- `dependency_health`: operation-linked availability, latency, and warnings;
  and
- neutral lifecycle logs with no diagnosis or invariant names.

Healthy controls complete before their varied deadlines and require no
compensation. One warned slow control still succeeds. A separate operation is
legitimately compensated only after its original execution is confirmed
cancelled, so compensation presence alone is not the answer.

## Hidden oracle

```text
observed_outcome = inconsistent_state
trigger = timeout_or_deadline
subsequent_action = compensation_or_rollback
failure_mechanism = incorrect_state_transition
affected_component = workflow_orchestrator
```

The orchestrator owns deadline policy, the compensation decision, and workflow
state. The executor only performs original execution and records its effect.
Oracle labels, component mappings, invariant definitions, expected evidence,
roles, and sensitive-field annotations stay outside `ModelView`.

## Temporal scope

The target visibly satisfies:

```text
dispatch < execution start < deadline < compensation start < original completion
```

RCA requires ordering, overlap, and deadline crossing, not literal calendar
dates, epochs, timezone strings, or original timestamp formatting. Timestamp
fields are therefore explicitly privacy-annotated, but no relative-time privacy
transformation is implemented in this checkpoint.

The mandatory `incident-003-temporal-ablation-v1` audit rewrites every timestamp
to a unique deterministic non-parseable marker. Temporal relations become
explicitly unavailable rather than being replaced with a different valid
timeline. It retains timestamp fields, identities, evidence IDs, links, row
membership, states, effects, compensation presence, aliases, warnings, and
messages. Chronological log-row position is also neutralized because it would
otherwise preserve event ordering after timestamp removal. Structured-source
row order remains unchanged. This is a mechanical construction audit, not
proof that no analyst can infer another explanation, and it is not the
prospective `relative-time-v1` privacy transformation.
