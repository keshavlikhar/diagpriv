## Causal story and oracle

The target workflow dispatches an operation whose downstream execution starts
normally and remains in progress. The orchestrator reaches its deadline and
starts compensation. Original execution subsequently succeeds, producing an
active effect while the workflow and compensation records say compensated.

The frozen v2 RCA oracle is:

```text
observed_outcome = inconsistent_state
trigger = timeout_or_deadline
subsequent_action = compensation_or_rollback
failure_mechanism = incorrect_state_transition
affected_component = workflow_orchestrator
```

The orchestrator owns the deadline, compensation initiation, and workflow state
transition. The executor records only execution progress/result and the
original effect. The evidence therefore avoids assigning deadline or
compensation policy to the executor, reducing the component-ownership ambiguity
observed in earlier families.

The separate Incident 003 v2 oracle for `rca-taxonomy-v3` is:

```text
observed_outcome = inconsistent_state
trigger = timeout_or_deadline
subsequent_action = compensation_or_rollback
failure_mechanism = incorrect_concurrency_control
affected_component = workflow_orchestrator
```

V3 selects concurrency control because the inconsistent outcome requires
original execution and compensation to overlap and both take effect. Correct
fencing, serialization, or cancellation enforcement would prevent that result.
The edge is not classified as a state-transition defect because the
inconsistency does not persist under serialized execution.

## Temporal patterns

The target mechanically satisfies:

```text
dispatch < execution_start < deadline < compensation_start < original_completion
```

The target execution and compensation intervals overlap positively. The active
effect is recorded after compensation starts. Compensation completion may occur
before or after original completion; neither variation changes the oracle.

Each successful control satisfies:

```text
dispatch < execution_start < original_completion < deadline
```

Successful controls create active effects and have `compensation_state =
not_started`. A separate legitimate-compensation control satisfies:

```text
dispatch < execution_start < deadline < cancellation_confirmation
         < compensation_start < compensation_completion
```

It has no original effect. This ensures compensation presence alone does not
identify the target.

## Diagnostic invariants

### Essential

| Invariant | Visible semantics |
|---|---|
| `target_deadline_precedes_original_completion` | Target deadline is strictly before execution completion. |
| `target_compensation_after_deadline` | Target compensation starts strictly after deadline. |
| `target_compensation_precedes_original_completion` | Compensation starts strictly before original completion. |
| `target_execution_compensation_overlap` | Positive-duration execution and compensation intervals overlap. |
| `target_success_after_compensation_start` | Active original effect is created after compensation starts. |
| `control_completion_precedes_deadline` | Every successful control completion/deadline pair is strictly ordered. |
| `control_no_compensation` | Every successful control has `not_started` compensation state. |
| `target_event_order` | The complete five-event target order above holds. |
| `target_inconsistent_state` | Compensated workflow + successful execution + completed compensation + active effect coexist. |
| `target_effect_presence` | Target effect row exists and is active. |
| `target_execution_success_state` | Original target execution reports success. |
| `target_and_control_operation_distinctness` | Target, healthy controls, and compensated distractor IDs are all distinct. |
| `target_operation_cross_source_identity` | Target workflow, execution, effect, compensation, and health rows link to one operation. |
| `control_execution_success_state` | Every successful control execution reports success. |

### Supportive

| Invariant | Purpose |
|---|---|
| `shared_orchestrator_role` | One visible orchestrator alias owns workflow/deadline/compensation rows. |
| `shared_executor_role` | One visible executor alias performs original operations. |
| `dependency_remained_available` | Dependency samples remain available despite warnings. |
| `successful_controls_bracket_target_chronologically` | Successful controls occur before and after target dispatch. |
| `benign_slow_control_succeeds_before_deadline` | A slower control still completes within deadline. |
| `benign_slow_control_warning` | A non-target success carries the latency warning. |
| `target_compensation_record_presence` | One completed target compensation record exists. |
| `legitimate_compensation_event_order` | Cancel confirmation precedes legitimate compensation. |
| `legitimate_compensation_terminal_state` | Cancelled execution is cleanly compensated. |
| `legitimate_compensation_effect_absence` | The compensated distractor has no original effect. |
| `target_workflow_state_cardinality` | Exactly one target workflow row provides final state. |

### Discardable

The declared discardable invariants are
`literal_target_dispatch_timestamp`, `literal_target_deadline_timestamp`, and
`exact_target_deadline_interval`. RCA needs the predeclared ordering, overlap,
and threshold crossing, not the original calendar date, wall-clock value,
timezone representation, Unix epoch, date-string format, or exact absolute
timestamp. No essential invariant requires preservation of a literal timestamp
or a particular timestamp string format.

## Temporal helper

`temporal-semantics-v1` accepts only explicit RFC 3339 timestamps with `T`,
seconds, optional fractional seconds up to microsecond precision, and either
`Z` or a numeric UTC offset. Naive datetimes, named zones, alternate separators,
invalid calendar values, and silent normalization are rejected.

The helper defines strict `before` and `after`, instant equality after timezone
interpretation, non-negative interval duration, strict or non-strict ordered
sequences, paired strict-before checks, and positive overlap of half-open
intervals `[start, end)`. Touching endpoints do not overlap; zero-length and
reversed intervals are invalid.

## Anti-shortcut and distractor design

- Four temporal templates vary deadlines, compensation delay, overlap duration,
  and compensation-completion ordering.
- Four to seven successful controls vary duration and absolute time.
- One non-target slow control always has elevated latency but succeeds before
  deadline; the target independently may or may not carry a warning.
- All dependency observations remain available.
- One cancelled operation is legitimately compensated and creates no original
  effect.
- Every operation has the same total number of structured rows plus log rows,
  preventing evidence count from naming the target.
- Structured sources are independently shuffled. Target chronological and row
  positions, aliases, date, identifiers, and log wording vary by seed.
- Neutral evidence contains none of the prohibited causal phrases, including
  “premature compensation,” “race condition,” “deadline bug,” or state-machine
  diagnoses.

The target's effect-plus-compensation combination objectively establishes the
outcome, but only temporal relations distinguish the intended causal mechanism
from the legitimate compensation and healthy controls.

## Temporal ablation

The deterministic audit-only ablation changes every timestamp value to a
unique, non-parseable marker of the form
`TA1::<source>::<evidence-id>::<field>`. Each timestamp field remains present,
but the marker carries no original timestamp and defines no before/after,
equality, duration, overlap, or global-timeline semantics. Unique markers avoid
the artificial equality that a uniform placeholder would create.

This unavailable-time representation replaces an earlier rejected approach
that reassigned valid timestamps. That approach could put successful target
completion before deadline and compensation after deadline, accidentally
introducing a new target-specific incorrect-transition clue. Non-parseable
markers cannot express that sequence or any other alternative ordering.

The strengthened audit enumerates raw and ablated relation profiles for every
operation. Before ablation, the target alone has the required deadline,
compensation, completion, overlap, and post-compensation-effect signature.
After ablation, every applicable temporal predicate for target and controls is
classified `unavailable`; no predicate is true, the post-success compensation
sequence is unavailable, and no target-unique true temporal predicate exists.

Because raw lifecycle logs are chronologically sorted, their original list
position is itself temporal evidence. The ablation therefore reorders the same
log records by neutral `(event_kind, evidence_id)` audit order. It verifies that
the raw target's causal event subsequence was present, that no operation retains
that subsequence afterward, and that every original log evidence ID remains.
This ordering is audit-only and must not be interpreted as an event timeline.

Operation identities, evidence IDs, cross-source links, results, states, row
cardinality, structured-source row order, source names, aliases, messages,
warnings, dependency state, effect presence, and compensation presence are
unchanged. Chronological log-row order is deliberately neutralized; log content
and membership are preserved. The audit still preserves the visible
inconsistent outcome, so it removes the intended temporal explanation rather
than deleting the symptom. Timestamp values, timestamp equality, ordering,
durations, overlap, threshold crossings, calendar information, and source
timestamp formatting are deliberately unavailable.

This ablation is a strong deterministic construction check, not a formal proof
that diagnosis is impossible without timing.

## Existing transformations and future relative time

Incident 003 annotates both identifiers and every timestamp-bearing path as
sensitive. Applying the unchanged existing implementations to canonical seed
1001 produces this offline behavior:

| Condition | Implemented timestamp behavior | Literal time removed | Temporal semantics |
|---|---|---|---|
| Raw | Leaves all 98 timestamp occurrences unchanged and parseable | No | All required temporal invariants hold |
| Redaction-v1 | Replaces each timestamp path with its generic placeholder | Yes | Timestamp evaluation rejects; relations are not preserved |
| HMAC-v1 | Produces path-scoped HMAC pseudonyms | Yes | Timestamp evaluation rejects; relations are not preserved |
| Tokenization-v1 | Produces path-scoped ordinal tokens | Yes | Timestamp evaluation rejects; relations are not preserved |
| Format-preserving-v1 | Pseudonymizes each path independently while retaining character pattern | Yes | Does not preserve calendar validity or cross-field ordering; canonical evaluation rejects |
| `relative-time-v1` | Shared-anchor exact millisecond offsets | Yes | All declared temporal relations genuinely preserved offline |

All rows are observations of offline code on this Incident 003 annotation
policy; they are not privacy-condition provider results. `relative-time-v1`
selects the earliest annotated ModelView timestamp as one shared `T+0ms` anchor
and emits canonical exact millisecond offsets. Its 200-instance audit passed
all 3,400 per-instance checks, and seed 1021 preserved the reviewed
equal-completion case. Calendar, wall-clock, timezone, epoch, and source
timestamp formatting are removed; exact relative gaps and spans intentionally
remain. Existing transformations were not changed to fit this family. See
`docs/relative_time_v1.md` for the protocol, threat accounting, alternatives,
hashes, and future dry-run configuration.

## Limitations

- This is synthetic construction with one raw model qualification and no human
  validation, privacy comparison, or revised-protocol qualification.
- A structured contradictory final state may make the outcome salient even
  though the intended mechanism still requires timing.
- Temporal ablation demonstrates loss of the declared mechanical clue, not
  impossibility of every alternate inference.
- Only RFC 3339 inputs and millisecond-generated examples are currently used.
- One family and 200 related development instances do not establish realism or
  generality.
- Existing baselines conflate timestamp removal with loss of temporal semantics;
  a matched temporal-privacy comparison needs a separately reviewed relative-
  time transformation.
